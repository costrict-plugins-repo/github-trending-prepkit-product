# Opportunity Solution Tree (OST)

Reference: Teresa Torres, *Continuous Discovery Habits*

## Structure

```
Desired Outcome (one only)
└── Opportunity 1 (unmet need / friction point)
    ├── Solution A
    │   └── Experiment → assumption tested
    └── Solution B
        └── Experiment → assumption tested
└── Opportunity 2
    └── Solution C
        └── Experiment → assumption tested
```

## Construction Rules

| Layer | What goes here | What does NOT go here |
|---|---|---|
| Outcome | One measurable product/business goal | Multiple goals, activity metrics |
| Opportunity | Unmet need, pain point, desire in user language | Features, solutions, "ability to..." |
| Solution | Specific capability or design that addresses one opportunity | Vague themes, "improve UX" |
| Experiment | Smallest test to validate key assumption of a solution | Full builds, MVPs before learning |

## Validation Checklist

- [ ] Only one outcome at the top
- [ ] Every opportunity is phrased as a user need, not a product feature
- [ ] Every solution maps to a specific opportunity (not directly to outcome)
- [ ] Every solution has at least one experiment defined
- [ ] Experiments test the riskiest assumption, not just the easiest one
- [ ] Tree was built with user evidence, not internal assumptions

## Common Mistakes

| Mistake | Symptom | Fix |
|---|---|---|
| Jumping to solutions | Solutions appear without opportunity layer | Add "what user need does this address?" before any solution |
| Features as opportunities | "Add dark mode" at opportunity layer | Rephrase as need: "struggle to read in low-light environments" |
| Multiple outcomes | Two goals at top competing for priority | Pick one; move others to a separate tree or backlog |
| No experiments | Solutions move straight to build | Define "what's the cheapest way to learn if this works?" |
| Outcome is an output | "Ship 3 features this quarter" at top | Replace with user/business outcome: "increase weekly active users" |
